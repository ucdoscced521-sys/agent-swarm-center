## 2. GitHub 上的常见做法（调研结论）

| 做法 | 谁在用 | 适用场景 | 代价 |
|---|---|---|---|
| **a. 根 README 单语（多数是英文）** | 绝大多数仓库 | 受众单一 | 母语读者体验差一点 |
| **b. 根 README + `README.<locale>.md`** | GitHub 官方文档推荐的形式 | 面向多语言受众的库/工具 | 两个文件要手动同步 |
| **c. `docs/<locale>/` 分语言目录** | 大型 OSS（Kubernetes、Vue 等） | 文档量大、有翻译团队 | 目录与链接复杂度上升 |
| **d. 主文档单语 + 翻译放在别处**（wiki / 独立 i18n 仓库 / Crowdin） | 有社区的项目 | 翻译由社区贡献 | 与代码不同步 |

**共同规律**：**README 一定是最先被读的那一份**，而它通常用英文；**越往下的设计/维护文档，越倾向于单语**——因为读者已被筛成了"要动手改代码的人"，而那批人通常直接看代码。

## 3. 双语还是单语？——本项目的选择与理由

**结论：只对"使用说明"做双语；其余单语（中文）。**

| 判断维度 | 分析 | 结论 |
|---|---|---|
| **谁是读者** | 使用说明的读者可能是**任何拿到这个包的人**（含非中文读者、外部评估者）→ 需要英文。设计/维护文档的读者只有维护者本人 → 中文够用 | ✅ 使用说明双语 |
| **维护成本** | 每加一个语言版本就多一份**必须同步**的副本。改一次协议要改 N 处 → N 越大越容易漂移 | ✅ 只双语那 1 份 |
| **翻译的保质期** | 技术文档的翻译**必然滞后**。语言越多，出现"英文说 A、中文说 B"的概率越高，而这种矛盾比缺翻译更糟 | ✅ 控制语言数量 |
| **要不要"全语种齐步走"** | 不必。**允许单语文档存在**，只要在索引里标明语言（本文件 §1 已列） | ✅ 索引标注语言 |
| **能不能靠工具** | 机器翻译可做**草稿**，但判定契约、归因码、成本数字这类内容**必须人工核对**，否则会写出"看起来对但语义错"的说明 | ⚠️ 人工把关 |

**反例（不要这样做）**：把所有文档都翻译一遍。结果通常是英文版停在 v0.1.0、中文版走到 v0.2.0，读者不知道该信哪份。

## 4. 命名规范

### 4.1 规则

| 规则 | 说明 |
|---|---|
| **新文档一律 ASCII kebab-case** | `05-usage-guide.md`、`00-doc-policy.md`。**不要**用空格、不要用 CJK 文件名 |
| **序号前缀保留** | `NN-` 保证目录里按阅读顺序排列，也让"引用编号"稳定（如"见 §11.2"） |
| **语言路由用目录而非后缀**（docs 内） | `docs/en/05-usage-guide.md` ↔ `docs/05-使用说明.md` |
| **语言后缀只用于根目录特殊文件** | GitHub 的既有约定：`README.md` / `README.zh-CN.md`、`CONTRIBUTING.md` / `CONTRIBUTING.zh-CN.md` |
| **为什么不用 CJK 文件名** | URL 会被百分号编码（`%E4%BD%BF%E7%94%A8...`），外部工具/脚本处理易出错；跨平台（老 Windows、CI 容器 locale）也有坑 |

### 4.2 存量中文文件名的处理

仓库里已有的 `05-使用说明.md`、`06-项目结构与维护指南.md` 等**保持不动（grandfather）**：

- 它们被 README、CHANGELOG、协议文档等多处引用，重命名会**同时破坏一批链接**，收益（好看）远小于风险（读者点开 404）
- **规则从新增文件开始生效**，不做一次性大迁移

**如果将来要做迁移**（可选，非必须）：按 §7 的步骤一次性做完，并在仓库根放 `docs/MIGRATION.md` 记录新旧路径对照表。

## 5. 存放位置规则

```
repo/
├── README.md                    ← 仓库入口（唯一"必读"入口；语言=受众主语言）
├── CHANGELOG.md                 ← 版本变更（单语即可；格式遵循 Keep a Changelog）
├── docs/
│   ├── README.md                ← ★ 文档地图 + 规范（本文件）
│   ├── 05-使用说明.md            ← 中文：面向一般用途（legacy 命名）
│   ├── 06-项目结构与维护指南.md    ← 中文：维护者文档
│   └── en/
│       └── 05-usage-guide.md    ← ★ English: general-purpose usage guide
└── swarm-lab/
    ├── VALIDATION-SUMMARY.md     ← 验证总报告（证据类文档，与代码同目录更合理）
    └── stepN-report.md           ← 每步报告
```

**四条放置原则**

1. **根目录只放"会被自动渲染"的文件**（`README.md`、`CHANGELOG.md`、`LICENSE`、`.gitignore`、`.gitattributes`）
2. **面向使用者的文档进 `docs/`**；**证据/报告与产生它的代码同目录**（所以 `stepN-report.md` 在 `swarm-lab/`，不在 `docs/`）
3. **翻译文件进 `docs/<locale>/`**，不要平铺在 `docs/` 里
4. **每份文档都要被索引到**——没在 §1 或根 README 里出现的文档，等于不存在

## 6. 后续更新流程（改文档必走）

```text
① 改中文版（主版本）  docs/05-使用说明.md
② 改英文版（同步）    docs/en/05-usage-guide.md
③ 若涉及版本号变化 → 同步 docs/README.md §1 与英文版 §14.1
④ 若新增/删除文档 → 更新 docs/README.md §1 与根 README 的文档索引
⑤ 提交（见下方 commit 约定）
⑥ 推送（见下）
```

**防漂移三条**

- **译文标注基线**：英文版头部写 `Translation baseline: <版本号 或 commit 短 hash>`。基线落后于主分支就该重新同步了
- **改中文没同步英文 → 不合并**：宁可英文版内容旧一点（有基线 hash 可查），也不要两份互相矛盾
- **数字只写一个地方**：版本号、断言计数、成本数字优先**放进表格**，避免正文里散落重复

**commit 约定（够用即止）**

```
docs: ...           纯文档
docs(en): ...       仅英文版
fix(docs): ...      修正错误信息
```

**推送**

```powershell
# 本仓库 remote 用 https://github.com:443/... 直连（:443 可绕过全局 url.insteadOf 的镜像改写），
# 并已在仓库级配好代理 http://127.0.0.1:7897
git push origin HEAD
git push origin --tags        # 发版时
```

> 若 `gh` 仍处于未登录状态（本仓库刻意未持久化凭据），首次推送前先：
> `powershell -File scripts/gh-device-auth.ps1 -Resume`

## 7. 可选后续动作（按需，不强制）

| # | 动作 | 收益 | 成本/风险 |
|---|---|---|---|
| 1 | **把根 README 英文化**，中文版另存 `README.zh-CN.md` | 面向外部读者时唯一正确的入口语言 | 中；需要重写 1 份 README 并加语言切换行 |
| 2 | 新增英文版维护指南 `docs/en/06-project-structure.md` | 外部贡献者能看懂结构 | 中；且维护指南本身迭代频繁，译文易过期 |
| 3 | 存量中文文档重命名为 ASCII | 链接与 URL 更规整 | **高**；会破坏多处在用链接，建议先出对照表 |
| 4 | 引入链接检查（CI 跑 markdown-link-check） | 自动发现失效链接 | 低；但本仓库无 CI，需本地脚本 |

**建议顺序**：先做 1（如果确实要让外部人看）→ 再考虑 4 → 2 和 3 长期不急。
