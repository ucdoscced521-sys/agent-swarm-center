## 1. 它能做什么 / 不能做什么

### ✅ 能做

- **一句话进，交付物出**：拆解 → 派人 → 执行 → 验收 → 收口，中途不问你
- **真并行**：多个子智能体同时跑，各自独立工作目录，绝不互相覆盖
- **可审计**：每一步判定都是结构化 JSON + 真实证据文件，口头汇报不算数
- **可续跑**：所有状态落磁盘，关掉对话、清空上下文后**只读 HANDOFF 就能接着干**
- **防自欺**：独立复核 + 三层闸门，专门拦"自己判自己 PASS"和"编造证据"

### ❌ 不能做（**重要，别误用**）

| 不能 | 原因 |
|---|---|
| 替代你做产品决策 | 它只在"信息不足且需要你拍板"时停下问**一个问题** |
| 保证界面"看起来对" | 无浏览器/视觉自动化时**没有** DOM 覆盖能力（会诚实标注） |
| 在单模型环境下做到完全异源 | 只能到 L2（不同会话+不同证据），到不了 L3（不同厂商） |
| 跨宿主直调（当前版本）| Codex→WorkBuddy CLI 通道在受限环境未通，走文件总线兜底 |
| 无限制地跑 | 有预算硬闸，超限会**暂停并上报**，不会自己续跑 |

## 2. 安装

专家包有 **5 个落点**，缺一不可。**第 2 项最容易被漏，但它才是运行时真正被加载的地方。**

| # | 落点 | 路径 |
|---|---|---|
| 1 | WorkBuddy 市场源 | `~/.workbuddy/plugins/marketplaces/my-experts/plugins/agent-swarm/` |
| 2 | **WorkBuddy 运行态 cache ★** | `~/.workbuddy/plugins/cache/my-experts/agent-swarm/<版本>/` |
| 3 | Codex 市场源 | `~/plugins/agent-swarm/` |
| 4 | Codex 缓存 A | `E:\codex\.codex\plugins\cache\personal\agent-swarm/<版本>/` |
| 5 | Codex 缓存 B | `~/.codex/plugins/cache/personal/agent-swarm/<版本>/` |

### 方式 A · 用同步脚本（推荐）

```powershell
# 权威源默认指向 <repo>/agent-swarm，可用 AUTHORITATIVE_SRC 覆盖
node swarm-lab/tools/sync-expert.mjs
```

脚本会：① 校验源内容是否含最新标记（**不最新就拒绝同步**）② 同步前自动快照 ③ 同步全部 5 个落点 + 兜底陈旧版本目录 ④ 逐文件字节比对确认一致。

### 方式 B · 手工安装

1. 复制 `agent-swarm/` 到落点 1
2. 在 `~/.workbuddy/plugins/marketplaces/my-experts/.codebuddy-plugin/marketplace.json` 的 `plugins` 数组里追加：

```json
{ "name": "agent-swarm", "source": "./plugins/agent-swarm",
  "policy": { "installation": "AVAILABLE" }, "category": "Engineering" }
```

3. 复制到落点 2、3、4、5
4. Codex 侧：

```powershell
codex plugin remove agent-swarm@personal   # 换版本必须先移除，否则会继续装旧版
codex plugin add agent-swarm@personal --json
```

### 安装后自检

```powershell
# WorkBuddy 侧
python <expert-manager>/scripts/validate_expert.py "<落点1路径>"

# Codex 侧：应看到 version 与包版本一致、installed/enabled 均 true
codex plugin list --json
```

> ⚠️ **`settings.json` 会被 WorkBuddy 异步移除**（实测补位后约 30 秒内消失）。
> 这不是损坏。**正确顺序：同步（含补位）→ validate → register → package。**
> 若 validate 报 `Team type must have settings.json`，重新跑一次同步脚本即可。

## 3. 怎么召唤

### WorkBuddy（图形界面，日常推荐）

1. 左侧栏点 **「专家」**
2. 进 **「我的专家」**
3. 找 **「蜂群调度中心」** → 点开 → 新对话
4. 直接丢一句话。预置提示词：

> 帮我完成这个任务，你自己拆解、自己派人、自己验收，中途不用问我。

另有两条预置：
> 用热度榜里最合适的专家来做这件事，并说明你为什么选它、备胎是谁。
> 接手上一阶段的进度：读取 .swarm/HANDOFF.md 和 brief.json 后继续推进。

### Codex

新开会话后**必须显式唤起**（不会自动激活）：

```
$agent-swarm:agent-swarm
```

> 若想让它自动生效，可把 `agent-swarm/agents-fragment.md` 注入你的 `AGENTS.md`
> （建议首尾各注一次以抵抗长上下文漂移，并加可识别标记便于回退）。**默认不注入。**

### 给它这三样，能少一轮追问

| 给什么 | 例子 |
|---|---|
| **工作目录** | "在 `D:\proj\xxx` 里做" |
| **交付物形态** | "产出可运行的脚本" / "产出一份 md 报告" |
| **硬性验收要求** | "必须在 Node 20 上跑通" / "不许改 DB schema" |

不给也行，它会用默认假设往下跑，并把假设记进"待验证项"。

## 4. 它会自动做什么

```
Phase 0 地基      写 .swarm/contract.md（含工作目录、预算、并发上限）+ 建目录骨架
Phase 1 侦察      扫本机可用的专家/技能/项目，出能力地图（热度榜排序）
Phase 2 拆解      拆成"可独立验收"的任务集 + 依赖图 + 每任务的验收标准
Phase 3 派单      ★ 先过"派单前自检 6 条"，再写自包含说明书，无依赖任务并行 spawn
Phase 4 回流判定  只读判定文件首部，调用 json-gate 三关判定
Phase 5 独立验收  按风险分级复核（R3 必核 / R2 抽检 / R1 免核）
Phase 6 失败升级  L1 重试 → L2 重述 → L3 换人 → L4 找你（禁止无限重试）
Phase 7 收口封板  冻结、产出 report.md（固定 8 栏）、写 HANDOFF + brief
```

### 它只在三种情况停下找你

1. 需要你决策且信息不足（**只问一个最关键的问题**）
2. 触碰预算/权限红线
3. 全部完成待你验收

## 5. 你会在磁盘上看到什么

所有状态落在工作目录的 `.swarm/`（**唯一事实源，不信对话**）：

```
<你的项目>/.swarm/
├── contract.md              环境契约：工作目录 / 预算 / 并发上限 / 判定契约
├── main-log.md              主日志（append-only）
├── decisions.md             决策记录（每条含决策 + 理由 + 预期效果）
├── HANDOFF.md               给零上下文新会话的交接（只写指针不写正文）
├── bus/
│   ├── inbox/<T>.task.md    派单说明书（自包含，路径全绝对）
│   ├── outbox/<T>.verdict.json  子智能体回流判定（唯一合法形态）
│   └── claims/<T>.claim     认领锁（防重复派单）
├── state/
│   ├── tasks.json           任务总账（<5KB，明细在 tasks.detail/）
│   ├── brief.json           一页状态（<2KB，新会话先读这个）
│   └── events.jsonl         事件流（真实时间戳，append-only）
├── evidence/<T>/            ★ 每个任务的证据（真实命令输出，不美化）
│   └── _scratch/            临时探查文件（不算证据，收口清理）
├── reports/                 侦察/拆解产物（agents.json / projects.json / plan.tasks.json）
└── experience/patterns.md   可复用经验
```

**关键认知**：你可以随时删掉对话历史，`.swarm/` 在就一切都在。

## 6. 判定契约：子智能体怎么"交作业"

子智能体**不允许**用自然语言汇报。唯一合法形态是 `.swarm/bus/outbox/<task-id>.verdict.json`：

```json
{
  "verdict": "PASS",
  "task": "T-003",
  "agent": "builder-core@workbuddy",
  "evidence": ["evidence/T-003/test-run.txt", "evidence/T-003/summary.json"],
  "metrics": { "exit_code": 0, "tests": "12/12", "duration_s": 83 },
  "independent_level": "N/A",
  "handoff": "下一位需要知道的最小信息，≤300 字"
}
```

**七个字段全部必填**，多一个少一个都算结构违规。

### 三层闸门（缺一不可）

| 层 | 防什么 | 归因码 |
|---|---|---|
| **结构层** | 拼写漂移（`PASSED`/`pass`）、**夹带未声明字段**、类型错 | `schema_violation` |
| **身份层** | **张冠李戴**（声明的是别的任务号）| `task_mismatch` |
| **事实层** | 假 PASS（判定合规但**证据是编的**）| `evidence_dangling` |

其余：`no_verdict`（没写）/ `malformed_json`（不是合法 JSON）。

### 两个细节

- `metrics.tests` **只放短标识**（≤64 字符）：✅`"88/88"` ❌`"全部通过，但有个边界没覆盖"`（结论文句写进 `handoff`）
- 判定文件**体积被 schema 钉死**（理论上限约 2.9KB，实测 180–250B）→ 主脑整文件读也不伤上下文

## 7. 异源分级与复核分级

### 7.1 异源分级（谁来复核）

| 级别 | 条件（**全部满足**） | 效力 |
|---|---|---|
| **L3** | 复核模型与产出模型**不同厂商** | ✅ 完全达标（**优先争取**）|
| **L2** | ① 不同会话 ② 不同 agent 身份 ③ **自己产出证据** ④ **未读产出人的判定与结论** ⑤ cwd 隔离 | ⚠️ **有条件达标**，**必须在 `handoff` 标注级别** |
| **L1** | 仅"不同 agent 身份" | ❌ **视为未验收**，只能算冒烟复读 |

- 复核人**必须如实声明**实际级别（写进 `independent_level`）
- **虚报级别等同造假**，比降级严重得多
- 主脑收口时必须统计各级别数量并写进报告

### 7.2 复核分级（要复核多少）

| 风险档 | 判定条件 | 复核要求 |
|---|---|---|
| **R3 高危** | 触碰真实数据/生产库、删除文件、改对外契约/公开 API、改 DB schema | **必须独立复核**，不可豁免 |
| **R2 中危** | 新增功能、改核心逻辑、改测试 | **抽检 ≥50%**，其余靠可复现证据 + 闸门 |
| **R1 低危** | 文档、注释、文案、格式化、只读审计 | **免独立复核**，但须在报告标注"R1 免复核"及理由 |

**硬规矩**：
- R1 免复核 → 计入验收（标注豁免理由）
- **R2/R3 该复核却没有 → 不计入验收，且不得收口**

## 8. 成本纪律：怎么不烧钱

**实测基准**：一次小项目跑出 **1h46m / ≈200 积分** —— 偏高。**钱主要不是花在干活上，是同一份信息被反复搬运。**

### 八条纪律（agent 会默认执行）

| # | 纪律 | 预计省 |
|---|---|---|
| **S1** | **复核分级**（R3 必核 / R2 抽检 / R1 免核）| **30–40%** ← 唯一大杠杆 |
| **S2** | **证据摘要化**：>8KB 输出不进回流，只回 `{exit_code,用例数,失败数,首条失败}` + 路径 | 10–20% |
| **S3** | **测试一次跑、多处引用**（同一 wave 内）| 10% |
| **S4** | **读取预算**（默认 ≤15 文件 / ≤12 命令）+ **禁止全仓 grep** | 10–15% |
| **S5** | **模型分级路由**（侦察/拆解/书记/文档用快模型）| 5–15% |
| **S6** | **派单合并**（同文件内改动合并为一个任务）| 5–10% |
| **S7** | **收口冻结**（收口后不得再派单）| 5% |
| **S8** | **主账瘦身**（`tasks.json` <5KB，明细按需读）| 5% |

**合计预期省 45–60%**（≈200 → 80–110 积分）。

### 🔴 红线

**省钱只能省"重复劳动与上下文"，不能省"证据与复核"。**
一旦为了省钱把校验放松，前面所有验证工作就白做了。

### 建议写进 `contract.md` 的预算

```
BUDGET:
  单任务时限 ≤ 10 min ｜ 单阶段迭代 ≤ 2 轮
  单任务读取 ≤ 15 个文件 ｜ 单任务命令 ≤ 12 条
  全局 token 上限 ≤ 300k（超限暂停并上报）
CONCURRENCY: 3（上限 5）
VERIFY: R3 必核 ｜ R2 抽检 50% ｜ R1 免核(留痕)；异源目标 L3，达不到用 L2 并标注
```

## 9. 怎么看结果

每次收口必产 `report.md`（路径写在 `HANDOFF.md` 里），**固定 8 栏**：

| # | 栏目 | 你会看到什么 |
|---|---|---|
| 1 | 范围 | 做了什么 / **明确没做什么** |
| 2 | 交付物 | 绝对路径清单 |
| 3 | 验收结果 | 逐条：标准原文 → 判定 → 证据路径 |
| 4 | **复核覆盖与异源级别** | 数字形式，如 `L3×2 / L2×8 / L1×0 / R1豁免×2`，并给覆盖率 x/y |
| 5 | **未验项（诚实边界）** | 每条可证伪，含"怎么验" |
| 6 | 风险与遗留 | 含"红线邻近动作" |
| 7 | **成本** | 派单数 / 复核数 / 估算 token / **与预算对比** |
| 8 | next actions | 新会话第一批可执行动作 |

### 三个"健康度"数字，一眼看出它有没有偷懒

1. **复核数 ÷ 派单数** —— 接近 1:1 说明 **S1 没生效**（在浪费钱）；远低于 0.5 要警惕漏核
2. **第 4 栏有没有数字** —— 写"已独立复核"而没有级别数字 = 不合格
3. **第 5 栏是否非空** —— 一条未验项都没有，通常意味着**在藏问题**，不是做得好

## 10. 故障排查

| 现象 | 原因 | 处置 |
|---|---|---|
| `Team type must have settings.json` | WorkBuddy 异步移除了市场源里的 `settings.json` | 重跑一次同步脚本（末尾会自动补位）|
| 召唤后还是旧行为 | **运行态 cache 没同步**（最常见的坑）| 跑同步脚本；核对 cache 与源逐文件字节一致 |
| Codex 装完版本还是旧的 | 市场源清单没更新 / 没先 remove | 确认 `.codex-plugin/plugin.json` 版本号；`plugin remove` 再 `add` |
| 主脑过闸全报 `no_verdict` | **双调度根**：说明书写了相对路径，产出人在自己 cwd 另建了 `.swarm/` | 说明书里 `SWARM_DIR` 一律写**绝对路径** |
| 判定被拒 `schema_violation` | 字段拼写/夹带/超长 | 按 §6 的 7 字段模板重发；`tests` 只放短标识 |
| 并发度算不出来 | `events.jsonl` 字段名不对或时间戳是合成的 | 用 `ts/event/task/actor`，`ts` 必须真实时刻 |
| 反复重发判定 | 验收标准与"禁止写"的范围打架 | 这是**派单方**的问题（见 §11 自检 6 条）|
| 卡住很久不结束 | 命中长时任务的常态，非故障 | 看 `.swarm/state/brief.json` 的进度；或直接问它当前卡在哪 |

**通用排查三步**：① 看 `.swarm/state/brief.json`（一页状态）② 看 `.swarm/main-log.md` 尾部 ③ 看 `decisions.md` 尾部最近的决策。

## 11. 日常维护

### 11.1 改完提示词必须做的一次自检（否则一定会踩）

**派单前自检 6 条**（协议已强制，你改提示词时也要遵守）：

```
□ 路径全部绝对？（SWARM_DIR 绝不写相对）
□ 验收标准与"禁止写"范围是否冲突？
□ 说明书内部有无互斥条目？
□ 引用的契约是否唯一来源？（没有第二份"差不多"的 schema）
□ 判据是否写死了会过期的字面值？（应作"exit 0 且 0 失败"）
□ 违反约束才能满足标准时，产出人该怎么办？→ 已写明"上报，禁止硬凑 PASS"
```

> **实测教训**：一次真实运行里契约层失误 **5 次**，**主脑自查 0 次**，全部由下游先发现，失误率约 **19%**。

### 11.2 升级版本的完整流程

```powershell
# 1) 改版本号（两处）
#    agent-swarm/.codebuddy-plugin/plugin.json
#    agent-swarm/.codex-plugin/plugin.json

# 2) 同步到 5 个落点（脚本会自动读版本号 + 兜底陈旧目录）
node swarm-lab/tools/sync-expert.mjs

# 3) 校验 → 注册 → 打包
python <expert-manager>/scripts/validate_expert.py "<落点1>"
python <expert-manager>/scripts/register_expert.py "<落点1>"
python <expert-manager>/scripts/package_expert.py  "<落点1>"

# 4) 再同步一次（补位 settings.json）
node swarm-lab/tools/sync-expert.mjs

# 5) 接线校验（9 条断言）
node swarm-lab/tools/run-step6-wiring.mjs

# 6) Codex 侧换版本
codex plugin remove agent-swarm@personal
codex plugin add    agent-swarm@personal --json
```

### 11.3 改完协议必须跑的回归

```powershell
node swarm-lab/tools/run-step1.mjs   # 最小闭环 16/16
node swarm-lab/tools/run-step2.mjs   # 真并行   18/18
node swarm-lab/tools/run-step3.mjs   # 判定硬化  8/8
node swarm-lab/tools/run-step4.mjs   # 边界硬化 26/26
```

**改过 `schemas/verdict.schema.json` 还要额外过一次真 provider**（严格模式约束只有真模型才暴露）：

```powershell
node swarm-lab/tools/run-step5a.mjs 1
```

### 11.4 真实运行后的例行审计

```powershell
node swarm-lab/tools/audit-real-run.mjs "<你的工作目录>"
```

**不信它的 HANDOFF，用权威闸门把 outbox 全量重判一遍**，并核对协议产物（旧协议残留 / schema 漂移 / 双调度根 / 事件流 / 复核覆盖率）。

### 11.5 上传到 GitHub（含无 TTY 环境的坑）

```powershell
# 首次上传：自驱动设备码授权 → 建私密仓库 → 推分支 + 推标签
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/gh-device-auth.ps1 `
    -RepoName agent-swarm-center -CreateRepo

# 之后日常增量推送
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/push-to-github.ps1 -RepoName agent-swarm-center
```

脚本会打印**授权网址 + 一次性验证码**，你在浏览器里输入并点 Authorize 即可，其余全自动。

> ⚠️ **两个必踩的坑**
> 1. **`gh auth login --web` 在无 TTY 环境下必然失败**（`unexpected EOF` / `context deadline exceeded`），
>    验证码会进剪贴板但进程已退出 → 改用 `gh-device-auth.ps1`（自己驱动设备码流程）。
> 2. **`github.com` 直连可能不通、而 `api.github.com` 通**。`git push` 与设备码换 token 都走主站，
>    所以**必须给 git 和 gh 都配代理**（默认 `http://127.0.0.1:7897`，用 `-Proxy` 改）。
>    验证：`curl --proxy <proxy> -s -o NUL -w "%{http_code}" https://github.com/` 应返回 `200`。
>
> **安全**：脚本把 token 临时写在 `%TEMP%\gh-token.txt` 并在登录成功后立刻删除；
> 推送用**一次性认证头**（`git -c http.extraheader=...`），**不把凭据写进 `.git/config`**；token 从不打印。

## 12. 常见示例（可直接复制）

六个场景，**把方括号里的内容换成你自己的**即可。每个都标了"看什么算成功"。

### 例 1 · 首次试水：最小任务（推荐第一个跑这个）

> **目的**：验证它是否真在"拆解 + 派单 + 验收"，而不是自己一把梭。半小时内能看出结论。

```
帮我完成这个任务，你自己拆解、自己派人、自己验收，中途不用问我。

任务：给 [D:\proj\demo] 写一个 count-fields.mjs：
      读入一个 JSON 文件路径，输出它顶层字段的数量。
工作目录：[D:\proj\demo]
验收：node count-fields.mjs sample.json  → 输出 3 且 exit=0
      传入数组或不存在路径       → exit≠0
```

**看什么算成功**：`report.md` 第 4 栏有数字 → 它真的复核了；第 5 栏非空 → 它敢说没验什么。

---

### 例 2 · 真并行：三个互不依赖的子任务

> **目的**：验证"真并行"（而不是排队做）。

```
在 [D:\proj\site] 里做三件事，互不依赖，请并行推进：
1. 写 pages/index.html —— 纯静态，含标题 + 一段说明
2. 写 api/health.mjs  —— Node 20，GET 返回 {"ok":true}
3. 给上面两块各写一条冒烟测试
验收：每个子任务独立可验，证据各自落到 .swarm/evidence/<task-id>/
```

**看什么算成功**：`.swarm/state/events.jsonl` 里能算出**并发度 > 1**（多个 `task.start` 时间窗重叠）。

---

### 例 3 · 省积分：带预算 + 复核分级（最省钱的一招）

> **目的**：把"复核 1:1 全覆盖"这个最大成本项压下去。**文档类任务应该 0 复核。**

```
预算：最多 6 次派单、2 次复核，超了就停下问我。
复核按风险分级：R3 必核 / R2 抽检一半 / R1 免核但须留痕。
任务：把 [docs/] 里过期的版本号提示统一成 v0.2.0。
```

**看什么算成功**：`report.md` 第 4 栏出现 `R1豁免×N`，且**复核数远小于派单数**。若仍是 1:1，说明纪律没生效。

---

### 例 4 · 只读审计：不碰任何文件

> **目的**：审计已有运行记录，**明确禁止写**（避免它"顺手改点什么"）。

```
只读模式：禁止修改、创建、删除任何文件。
任务：审计 [C:\path\to\project] 的 .swarm 产物 ——
      用 swarm-lab/tools/audit-real-run.mjs 重跑一遍判定，输出一份 md：
      判定合规率 / 复核覆盖率 / 异源级别分布 / 未验项清单。
验收：报告里每个数字都能在磁盘上找到对应文件；给出文件路径。
```

**看什么算成功**：跑完 `git status` 应该**干净**（除了它自己产出的那份报告）。

---

### 例 5 · 换会话续跑（不重做已完成部分）

> **目的**：长任务跨会话接力。**它只读磁盘状态，不依赖对话记忆。**

```
接手上一阶段的进度：先读 [.swarm/HANDOFF.md] 和 [.swarm/state/brief.json]，
再继续推进，不要重做已完成的部分。
```

**看什么算成功**：它开头的动作是**读文件**而不是问你"之前做到哪了"。

---

### 例 6 · 结果不满意时，怎么说（推动它自查）

> **目的**：把"感觉不靠谱"变成可执行的整改指令。**不要只说"再检查一下"。**

```
你的 report.md 不合格，请重跑收口，不要改结论、只补证据：
- 第 4 栏缺数字 → 给出 复核覆盖 x/y 与 L1/L2/L3 分布
- 第 5 栏是空的 → 给出至少 2 条可证伪的未验项（含"怎么验"）
- 第 7 栏缺成本 → 补 派单数 / 复核数 / 与预算对比
证据补不出来的话，把对应验收改成 FAIL 并说明原因。
```

**看什么算成功**：新报告的第 4/5/7 栏有具体数字或明确 FAIL，而不是"已充分验证"这类空话。

## 13. 注意事项与已知边界

### 13.1 用之前必须知道的五条

| # | 注意 | 为什么 |
|---|---|---|
| 1 | **它是"多一次审查"，不是"多十双手"** | 便宜的活别交给它：多派一个人就多一份上下文成本 |
| 2 | **不要在它工作时改同一份文件** | 它有独立工作目录，你改主目录会造成合并冲突 |
| 3 | **判定只有一种合法形态**（JSON 过 schema）| 口头问"做好了吗"，回答一律不算判定 |
| 4 | **它说没验的就是真没验** | 见下方边界表；别把"未验项"当"已通过" |
| 5 | **收口后不要继续派活** | 封板已冻结，追加任务请重发说明书（协议 §3.1）|

### 13.2 已知边界

| # | 未验证 / 做不到 | 影响 |
|---|---|---|
| 1 | **真实业务长时运行** | 只在一次个人工作台项目上跑过完整一轮（26 派单 / 11 wave）|
| 2 | **跨宿主 CLI 通道**（Codex → WorkBuddy）| 受限环境下 `-p` 不执行一次性回合；现走文件总线兜底 |
| 3 | **L3 异源** | 单模型环境下只能到 L2；协议已改为分级并强制标注 |
| 4 | **前端视觉验证** | 无浏览器/DOM 自动化；界面正确性需人工走查，报告会显式标注 |
| 5 | 隔离用**独立目录**而非 `git worktree` | 功能等价，生产建议切 worktree（两宿主 CLI 均有 `-w`）|

> 这五条全部写进了 `HANDOFF.md` 的"诚实边界"栏 —— **它说没验的就是真没验，别当已经验过。**

### 14.3 兼容性与约束

| 约束 | 说明 |
|---|---|
| **Schema 严格模式** | 判定契约的每个 object 里 `properties` **必须全部**列进 `required`（provider 硬约束，不允许"可选字段"）|
| **改 schema 必须过真 provider** | 自家校验器通过 ≠ provider 接受。改完必须跑 `node swarm-lab/tools/run-step5a.mjs 1` |
| **双宿主版本必须同号** | 两处 `plugin.json` 不一致会导致 Codex 侧装成旧版 |
| **Codex 换版本需先 remove** | 直接 `add` 不会覆盖，必须先 `plugin remove agent-swarm@personal` |
| **包内不含凭据** | 无 token / 无密钥 / 无账号信息，可安全公开或私有存放 |

### 14.4 如何升级 / 如何确认装到了哪一版

- **升级流程**：见 [§11.2](#112-升级版本的完整流程)（改版本号 → 同步五落点 → 校验/注册/打包 → 补位 → 接线校验 → Codex 换版）
- **确认运行版本**（一眼看出有没有装旧版）：

```powershell
# WorkBuddy 侧：运行态 cache 才是真正被加载的那一份
(Get-Content "$env:USERPROFILE\.workbuddy\plugins\cache\my-experts\agent-swarm\0.2.0\.codebuddy-plugin\plugin.json" -Raw | ConvertFrom-Json).version

# Codex 侧
codex plugin list --json     # 看 version / installed / enabled
```

> ⚠️ **最常见的"装了新版没生效"**：只更新了市场源，**忘了运行态 `cache`**。跑一次 `node swarm-lab/tools/sync-expert.mjs` 会一次同步全部落点。
