# 「一主多子」多智能体协作插件 —— 开发方案 v1.0

> 状态：方案设计（本阶段不写代码）
> 输入素材：① 参考图《HTML 幻灯片多智能体开发系统 — 主智能体提示词》② 视频《Agent Loop: 多智能体协同，让AI长时工作，从原理到实践》(B站, 2026-04-26)
> 目标：主智能体做组织主体（拆解/分发/调度），N 个子智能体**真实独立并行**执行，状态实时回流，形成可持续运转的任务循环闭环，并支持按开发者文档从 P0 到 P5 持续推进 + 自主测试验证。

## 0. 结论先行

### 0.1 三条不可妥协的设计判决（先立规矩，再谈实现）

| # | 判决 | 理由（为什么这是唯一解） |
|---|---|---|
| **D1** | **循环归程序，决策归模型**：`while` 循环、并发、超时、重试由**本地常驻进程**负责；LLM 只在每一轮被"唤醒一次"做**一次策略决策** | 把循环交给 LLM（"你自己决定再起哪个 agent"）在长时运行下必然退化：上下文膨胀→遗忘调度→退化为串行→**伪协作**。程序负责"循环"，模型负责"智能"，两者职责不混 |
| **D2** | **状态归磁盘，不归上下文**：主智能体的全部记忆在 `.agent/state/`，不在对话历史里 | 这是"每阶段换新对话还能接着干"的**物理前提**。上下文是可丢弃缓存，磁盘才是真相源（SSOT）。做不到这条，你说的"交接上下文"就永远靠人肉复述 |
| **D3** | **能力剥夺优先于行为禁止**：主智能体"不写代码"不靠提示词自律，靠**工具白名单**让它写不了 | 参考图用"绝对禁止清单"（✗不编辑代码）——那是提示词层约束，长上下文下会被稀释。工程层约束（主 Agent 的 worker 根本没挂 Read/Write/Edit 代码的工具）是**一个数量级的可靠性提升** |

### 0.2 推荐路线（一句话）

> **B 方案：外部 Loop Engine（Node 常驻进程）+ CLI Worker 进程池（5 并发槽位）+ git worktree 隔离 + SQLite/JSONL 状态库 + 主智能体每次被唤醒只吃 2KB 状态摘要。**

Codex 不是"跑 5 个常驻实例"，而是**一个进程池按需 spawn 5 个一次性 CLI 子进程**——每个子进程天然拥有独立进程、独立上下文、独立工作目录，这才是"真独立并行"。

### 0.3 落地节奏

P0 → P1 → P2 → P3 → P4 → P5 六个里程碑，**每阶段：一道自动 Gate + 一次人工 GO + 一次强制交接（开新对话）**。

## 1. 整体架构设计与主/子智能体职责边界

### 1.1 分层图

```
                    ┌───────────────────────────────┐
   人在环 (你)  ────│  只做两件事：① 下 GO ② 阶段验收 │
                    └───────────────┬───────────────┘
                                    │  (唯一人工闸口)
┌───────────────────────────────────▼────────────────────────────────────┐

│  │Scheduler │ Worker    │  Gate     │ Watchdog │ Event Log │  Budget  │ │

   │ W-01   │ │ W-02   │ │ W-03   │ │ W-04   │ │ W-05   │  独立上下文窗口
   │ DEV    │ │ DEV    │ │ TEST   │ │VERIFY  │ │ SCRIBE │  独立 git worktree

        │  main-log.md         人读时间线                │
        │  state/tasks.json    任务状态机                │
```

### 1.2 三个角色的职责边界（冻结契约）

| 角色 | 是 LLM？ | 输入 | 输出 | 允许的工具（白名单） | 绝不触碰 |
|---|---|---|---|---|---|
| **L0 Loop Engine** | 否（程序） | `state/tasks.json` + `events.jsonl` | 进程 spawn、状态迁移、Gate 执行结果 | 文件系统、进程管理、测试执行 | 不做任何语义判断、不调 LLM |
| **L1 主智能体（Organizer）** | **是** | **仅** 状态摘要 brief（≤2KB）+ 阶段目标 + 上一轮 `next_actions` 执行结果 | `next_actions[]`（JSON：派谁、干什么、验收什么） | 只读 brief、写 `decisions.md`、调用 `engine.dispatch` | 读代码正文 / 读素材 / 编辑任何文件 / 执行测试 |
| **L2 子智能体（Worker）** | **是** | `inbox/<task-id>.task.md`（单任务说明书） | `outbox/<task-id>.verdict` + 实际产物 + 证据 | 全量读写（限自己 worktree）、跑命令、跑测试 | 与其他 worker 通信、修改 `state/`、越权改别人 worktree |
| **L3 Gate（验收门）** | 否（程序）/ 可配异源 LLM | worker 产物 + 证据 | `PASS` / `FAIL` + 理由 | 执行测试、比对 schema、校验哈希 | 不做主观审美判断（那交给 Verifier 角色） |

**关键点**：主智能体是**无状态**的。它的"人格连续性"来自磁盘，不来自对话。因此它每次被唤醒时读的东西完全一样（brief），换新对话、换新模型、换新设备都不影响。

### 1.3 五类子智能体（角色卡）

| 角色 | 并发槽 | 建议模型档位 | 职责 | 完成判据 |
|---|---|---|---|---|
| `planner` | 1（串行） | 高 | 把阶段目标拆成任务 DAG，写 task 说明书 | 产出 `tasks.json` 增量 + 依赖关系合法（无环） |
| `dev` | 2–3（并行） | 中 | 按 task 说明书实现，产出代码/文档 | 产物存在 + 自测通过 + verdict=PASS |
| `test` | 1–2（并行） | 中 | 独立编写/执行测试，产出覆盖率与报告 | 测试可复现执行 + 报告落 `evidence/` |
| `verify` | 1 | **异源模型**（与 dev 不同厂商） | 独立复核：读产物与证据，判定是否真达标 | 出 `### 判定: PASS/FAIL` + 反证或反驳说明 |
| `scribe` | 1 | 低 | 维护 `main-log.md` / `HANDOFF.md` / 文档 | 交接文档齐全、栏目无缺 |

> **为什么 `verify` 必须异源**：同一个模型验收自己（或同族模型）的产出，存在系统性同源盲区——它会用"生成时的同一套错误假设"去验收。异源模型是"写 bug 的人修 bug、提 bug 的人验收"的强化版，成本极低、收益极高。

### 1.4 任务粒度原则（替代参考图的 BATCH_SIZE）

- **一个任务 = 一个可独立验证的产物**（一个文件、一个函数、一份文档、一条测试）。
- 默认粒度：单 task 预期 token 消耗 ≤ 单 worker 上下文的 40%，留出余量给自测与纠错。
- **动态批量**：Gate 一次通过率 ≥ 80% → 允许合并小任务；一次通过率 < 50% → 强制降为最小粒度（对应参考图 BATCH_SIZE 默认 1 的思路，但由数据驱动而非人工指定）。

## 2. 任务分发与状态回流的流转机制

### 2.1 状态机（冻结）

```
  PENDING ──dispatch──> DISPATCHED ──worker起──> RUNNING
                             │                      │
                             │  spawn失败           ├─ 完成 ──> SUBMITTED
                             ▼                      │            │
                          FAILED <──── timeout ─────┘        Gate 执行
                             │                                   │
                             │                            ┌──────┴──────┐
                             │                          PASS           FAIL
                             │                            │              │
                             │                        DONE(存档)     RETRY(≤3)
                             │                                          │
                             │                                    3次仍FAIL
                             ▼                                          ▼
                        （重试 或 升级）                          ESCALATED ──> 人工 GO/改派
```

状态字段（`state/tasks.json` 单条）：

```json
{
  "id": "P2-T03",
  "phase": "P2",
  "role": "dev",
  "deps": ["P2-T01"],
  "goal": "实现 worktree 隔离层",
  "acceptance": ["单测通过", "两 worker 并发改同文件不冲突"],
  "status": "RUNNING",
  "attempt": 1,
  "worker": { "pid": 18342, "session": "codex-xxxx", "worktree": "wt/P2-T03" },
  "artifacts": [],
  "verdict": null,
  "started_at": "20260926 10:12",
  "ended_at": null,
  "tokens": 0
}
```

### 2.2 三条回流通道（互不替代，各有分工）

| 通道 | 载体 | 写入者 | 读取者 | 用途 | 为什么需要它 |
|---|---|---|---|---|---|
| **① 事件流** | `state/events.jsonl`（append-only，一行一事件） | Engine 自动 + worker 由 hook 写 | Engine、可视化面板 | 实时进度、并行度计算、审计 | **机器可读**是"实时回流"的字面实现；手写日志必漏必错 |
| **② 判定文件** | `outbox/<task-id>.verdict`（首行必须是 `### 判定: PASS\|FAIL`） | worker 自己 | Gate、主智能体（**只取首行**） | 结论传递 | 借鉴参考图的核心技巧：主智能体用 Grep 只抓首行，**不读正文**，上下文零污染 |
| **③ 状态库** | `state/tasks.json` / SQLite | Engine 唯一写入者 | 所有人 | 断点续跑、依赖调度 | 进程崩溃后能恢复的唯一依据 |

### 2.3 单轮循环的完整时序（Tick Loop）

```
 ① Engine tick（每 3s）
      └─ 读 tasks.json，找 status=PENDING 且 deps 全 DONE 的任务
 ② 并发控制
      └─ 空闲槽位 = N；取 |空闲槽位| 个任务（按 phase → 优先级 → 依赖深度排序）
 ③ 派发 dispatch
      ├─ git worktree add wt/<task-id>  （物理隔离，防互相覆盖）
      ├─ 写 inbox/<task-id>.task.md     （只放这一条任务的说明书 + 验收标准）
      ├─ spawn 子进程：codex exec / claude -p --print（独立上下文）
      └─ 记事件 {type:task.dispatch, pid, ts}
 ④ worker 执行（真并行；互不可见）
      ├─ 干活 → 写产物
      ├─ 自测 → 写 evidence/<task-id>/
      └─ 写 outbox/<task-id>.verdict（首行判定 + 证据路径 + 复杂度自评）
 ⑤ Engine 回收（进程 exit）
      ├─ 校验 verdict schema 合法？证据文件真实存在？哈希对得上？
      ├─ 无证据 = 直接判 FAIL（反"假 PASS"）
      ├─ 跑 Gate（自动化验收命令）
      └─ 迁移状态 → DONE / RETRY / ESCALATED，写事件
 ⑥ 屏障判断 barrier
      ├─ 未到屏障（本阶段还有 PENDING/RUNNING）→ 回 ①
      └─ 到了屏障（本阶段全部 DONE 或 ESCALATED）→ ⑦
 ⑦ 主智能体唤醒（唯一 LLM 决策点）
      ├─ Engine 生成 brief：只含 {阶段目标, 任务统计, FAIL 清单+首行判定, 未决问题, 预算余量}
      ├─ 主智能体 → next_actions[]（派谁 / 干什么 / 验收什么 / 或宣告阶段完成）
      └─ Engine 校验 next_actions 合法性（角色存在、依赖合法、不越权）后执行 → 回 ①
```

### 2.4 闭环持续运转的 8 条保障（缺一条就会停摆或空转）

| # | 保障机制 | 具体做法 | 防范的失败模式 |
|---|---|---|---|
| 1 | **心跳 + 断点续跑** | Engine 每 tick 落盘；启动时先读 `state/` 恢复，孤儿 RUNNING 任务重置为 PENDING | 进程崩溃 / 换新对话后循环断掉 |
| 2 | **依赖屏障 + 阶段门** | 任务 DAG 无环校验（启动即校验，有环直接拒启）；每阶段末必须过 Exit Gate | 乱序执行、跳阶段偷跑 |
| 3 | **四级失败升级** | RETRY（换提示词）→ REFORMULATE（planner 重拆任务）→ ESCALATE（换角色/换模型）→ HUMAN（转 PAUSED 交你） | 无限重试烧钱 / 卡死 |
| 4 | **预算熔断** | 三重上限：token、墙钟时长、单任务迭代次数；任一超限 → 全池 PAUSED | 无人值守时烧光配额 |
| 5 | **反假 PASS 守卫** | verdict 无证据文件 / 证据哈希不符 / 测试退出码≠0 / 单测覆盖率下降 → 一律降级为 FAIL | worker 编造 PASS（LLM 天然倾向"报喜"） |
| 6 | **防空转守卫** | 连续 K 轮（默认 3）无新增 diff 且无状态迁移 → 判定空转，触发 REFORMULATE | 死循环空跑 |
| 7 | **孤儿/僵尸回收** | 单任务墙钟超时（默认 20min）→ kill 进程树 + 标记 FAIL + 清理 worktree | 挂起进程占满槽位 |
| 8 | **人工闸口** | 每阶段末 Gate 通过后**不自动进下一阶段**，等你的 GO | 失控扩散；符合"每阶段一次确认"的节奏 |

### 2.5 "真并行"的证明方式（对伪协作的硬性验收）

这是你最在意的点，所以必须**可测量**，不能靠感觉：

| 指标 | 计算方式 | 真并行 | 伪并行（同一模型轮流扮演） |
|---|---|---|---|
| **M1 并发度** | Σ(各任务执行时长) ÷ 阶段墙钟时长 | ≈ 2.5–4.0 | ≈ 1.0（严格串行） |
| **M2 时间线重叠** | `events.jsonl` 中两两 worker 的 `[start,end]` 区间是否重叠 | ≥2 区间同时重叠 | 无任何重叠 |
| **M3 进程证据** | 阶段内随机 3 次快照 `任务管理器/ps` 的 CLI 子进程数 | ≥2 | =1 |
| **M4 上下文隔离** | 对比 worker A 的 prompt hash 是否出现在 worker B 的 prompt 里 | 无交集 | 有交集/共享大段前缀 |
| **M5 冲突暴露** | 两 worker 同时改同一文件，是否产生真实 git 冲突/需合并 | 会产生（故需 worktree 隔离） | 不会——因为压根没同时跑 |
| **M6 session 独立性** | 每个 worker 的 session id / PID 是否唯一且生命周期独立 | 唯一、独立退出 | 共享一个会话 |

> **验收硬指标**：P2 阶段 Exit Gate 必须任选一个 M1（≥2.5）、M2、M3 三者中**至少两项**达标并落 `evidence/parallelism-proof/`，否则 P2 不通过、不许进 P3。
> 这条设计的目的：**让"伪协作"在数字上无处藏身**。

## 3. 工具与环境建议

### 3.1 三方案对比

| 维度 | **A 纯宿主 subagent** | **B 外部 Loop Engine + CLI Worker（推荐）** | **C 队列化 + 容器/多机** |
|---|---|---|---|
| 实现方式 | 靠 Codex/Claude Code 内建 agent 工具，在单轮里并发起多个 subagent | Node 常驻进程，把 `codex exec` / `claude -p` 当**一次性工作进程** spawn | Redis/BullMQ + Docker + 多机 worker |
| 真并行 | 有限（同轮并发，宿主等待，关闭对话即断） | **强**（独立 OS 进程 + 独立 worktree + 独立 session） | 最强 |
| 断点续跑 | 弱（状态在对话上下文里） | **强**（状态在磁盘） | 强 |
| 换新对话交接 | 差（要人肉复述） | **好**（读 HANDOFF.md 即恢复） | 好 |
| 上下文卫生 | 中 | **好**（主 Agent 只吃 brief） | 好 |
| 落地成本 | 最低（半天） | 中（1–2 周，P0–P5） | 高（数周 + 运维） |
| 适用 | 原型验证、轻量任务 | ✅ **你的场景** | 团队/多机/生产级 |
| 主要缺陷 | 易退化为伪协作；长时运行不成立 | 需要自己写调度内核（本方案的核心工作量） | 现阶段**过度设计** |

### 3.2 推荐栈（B 方案具体清单）

| 层 | 选型 | 说明 / 理由 |
|---|---|---|
| 运行时 | **Node.js 22 LTS**（本机已有） | 与 Codex CLI 生态一致；`child_process.spawn` 管进程池最顺 |
| 语言 | TypeScript（编译产物给 Engine 用） | 状态机 + schema 校验需要类型 |
| Worker 宿主 | **Codex CLI**（`codex exec`）为主 | 你在用 Codex，且已有 CC Switch 代理链路；子进程模式天然隔离 |
| 兼容宿主 | Claude Code（`claude -p --output-format stream-json`） | **保留双宿主抽象**：Engine 只依赖 `WorkerDriver` 接口，防止锁定单一厂商（也便于 verify 用异源模型） |
| 并发槽位 | 默认 **5**（planner 1 / dev 3 / test-verify 2 实际并发上限取 min(配额, CPU×1.5)） | 不是 5 个常驻实例，是 5 个"同时最多在跑的进程"；任务完成即退出 |
| 隔离 | **git worktree**，每 task 一个 `wt/<task-id>` | 真并行必然带来写冲突；worktree 是唯一低成本的物理隔离方案 |
| 状态存储 | **SQLite**（任务/尝试/票据）+ **JSONL**（事件流）+ **JSON**（人读快照） | SQLite 抗崩溃、可查询；JSONL 顺序追加最适合事件流；JSON 给人看 |
| 任务下发 | `inbox/<task-id>.task.md`（单任务说明书） | 只给一个任务、只给必要上下文——粒度小才能上下文干净 |
| 验收 Gate | 直接跑项目测试命令 + 自定义断言脚本 | 自动、可复现、退出码即结论 |
| 可观测 | **TUI（首选，终端内）**：槽位占用、任务状态、并行度实时值 | 先 TUI 后 Web，避免早期投入浪费在 UI 上 |
| 预算 | 自建 token 计数（从 CLI JSON 输出读 usage）+ 墙钟 | Codex/Claude CLI 的 stream-json 均给 usage |
| 版本控制 | Git + Gitee（沿用你的既有习惯）；`.agent/` 是否入库需定（建议事件流不入库，模板入库） | |

### 3.3 关于"Codex + 5 个子智能体实例"的直接回答

- ❌ **不要**跑 5 个常驻 Codex 实例：常驻会话上下文只增不减、配额持续消耗、僵尸风险高、重启即失忆。
- ✅ **要**建一个 5 槽位的**进程池**：任务来 → spawn 一个 `codex exec` 子进程（自带独立上下文）→ 干完写 verdict → exit。
- ⚙️ **仅当**某角色需要"跨任务记忆"（如 planner 需要记住拆解风格、verify 需要积累"过往踩坑"），才对该角色启用 **session 续接**（`--continue` / resume session id）+ **经验库文件**（`knowledge/patterns.md`，由 scribe 维护、每次注入到该角色 prompt 尾部）。这正是视频里"经验库让 AI 越做越好"的落地方式。

## 4. 对参考图提示词的借鉴点与改进思路

|---|---|---|---|
| 1 | 主 Agent 只调度不干活 | ✅ **正确，直接继承** | 从"提示词自律"升级为 **D3 能力剥夺**（工具白名单），并给主 Agent **只读 brief** 的接口，让"不读产出"不再是纪律而是 API 设计 |

| 11 | 左栏 5 条《PROMPT DESIGN》设计法 | ✅ 通用且好用 | 直接吸收为本项目**所有子智能体 task 说明书的强制模板**（见 4.1） |

## 6. P0 → P5 阶段规划与 Exit Gate

> 原则：**每阶段的 Exit Gate 全部由自动化判据组成**（可脚本执行、退出码/断言即结论），人工只需在 Gate 通过后点一次 GO。每阶段结束**强制交接新对话**（见第 8 节）。

### P0 — 地基（无 LLM，纯协议）
**产出**：仓库骨架；`state/` schema 定义；`events.jsonl` 事件字典；`inbox/outbox/verdict` 文件协议；主/子/Role 契约文档；CLI 骨架（`agent init / status / log`）。
**Exit Gate（全自动）**
- G0.1 事件 schema 校验：所有事件类型都有 JSON Schema，样例事件全部通过校验
- G0.2 verdict 协议单测：合法 verdict 通过、缺失首行/缺证据 → 拒绝
- G0.3 `agent init` 幂等：连跑 3 次结果一致，无残留
- G0.4 文档完整性：角色契约、状态机图、事件字典三份齐备

### P1 — 单 Worker 贯通（打通一根链条）
**产出**：spawn 1 个 worker 跑通 `dispatch → 执行 → verdict → Gate → 状态迁移` 全链路。
**Exit Gate**
- G1.1 端到端冒烟：1 个任务（如"写一个 hello 函数 + 单测"）自动完成并落 `DONE`
- G1.2 失败路径：故意注入 FAIL 的 fake worker → 状态正确迁移到 RETRY，且**未产生假 PASS**
- G1.3 证据校验生效：删掉证据文件后重跑，判定必须从 PASS 翻转为 FAIL
- G1.4 幂等与恢复：kill Engine 后重启，任务从 PENDING 正确续跑

### P2 — 真并行（本项目的"命门"）
**产出**：N 槽位进程池；worktree 隔离；依赖屏障；并发安全。
**Exit Gate**
- G2.1 5 个任务同时派发，**M1 并发度 ≥ 2.5** 且 **M2 时间线重叠**存在，证明落 `evidence/parallelism-proof/`
- G2.2 进程证据 M3：阶段内 ≥2 次快照显示 ≥2 个 worker 子进程
- G2.3 冲突安全：两任务故意改同一文件，worktree 隔离下**不互相污染**；合并流程可复现
- G2.4 上下文隔离 M4：worker prompt 互相无交集（脚本比对）
- G2.5 僵尸回收：注入一个 sleep 超时任务 → 被 kill、标记 FAIL、槽位释放
- G2.6 **反伪协作红队测试**：把 WorkerDriver 换成"串行假实现"，Gate 必须**报 FAIL**（证明指标真的能识别伪并行）

### P3 — 主智能体决策环
**产出**：brief 生成器；主智能体唤醒-决策-next_actions 解析与合法性校验；决策日志。
**Exit Gate**
- G3.1 闭环跑通：≥3 轮"屏障 → brief → 决策 → 派发 → 屏障"自动循环无人工介入
- G3.2 **上下文预算**：主智能体单轮 brief ≤ 2KB，且**不含任何产物正文**（脚本扫描断言）
- G3.3 非法决策防御：注入越权/依赖非法的 next_actions → 被拒且记事件，不污染状态
- G3.4 决策可追溯：每轮决策理由写入 `main-log.md`，与 `events.jsonl` 时间戳对齐

### P4 — 质量控制（把"假 PASS"彻底堵死）
**产出**：异源 Verifier 角色；反假 PASS 守卫；四级失败升级；经验库。
**Exit Gate**
- G4.1 异源验证：Verifier 与 Dev 模型不同源，且对 3 个"表面上 PASS 但实际有缺陷"的样本全部判 FAIL
- G4.2 升级链路：构造一个必失败任务 → 完整走完 RETRY→REFORMULATE→ESCALATE→HUMAN 四级且状态可查
- G4.3 防空转：注入空转任务 → K 轮后触发 REFORMULATE
- G4.4 经验库生效：第 2 次遇到同类失败时，prompt 中自动带上历史经验条目（可断言）

### P5 — 长时自主 + 交接 + 可观测
**产出**：预算熔断；阶段 Gate 编排；HANDOFF 交接协议与生成器；TUI 面板；连续运行压测。
**Exit Gate**
- G5.1 **长时压测**：连续运行 ≥ 2 小时无人值守不崩、不死锁、不空转（事件流无异常间隙）
- G5.2 预算熔断：人为设低预算 → 正确 PAUSED 并保留可续跑状态
- G5.3 **交接有效性（最关键的 Gate）**：在阶段中途**关闭对话、清空上下文**，只读 `HANDOFF.md` + brief，在**新对话**中成功继续推进，且任务状态零错乱
- G5.4 TUI 可观测：槽位/任务/并行度/预算四项实时可见
- G5.5 阶段编排：跑完一个完整 phase（含 Exit Gate）后正确停在人工 GO 处

### 6.1 阶段推进的元规则
1. **Gate 不通过不进下一阶段**，禁止"先跳过回头补"。
2. 每阶段结束 → **写 HANDOFF.md → 开新对话**（第 8 节）。
3. 阶段目标本身也由主智能体拆解（`planner`），但**阶段定义与 Gate 由人冻结**（防止模型自行降低验收标准——这是最需要防的自我放水）。

## 7. 自主测试与验证能力（系统如何自证）

| 层 | 手段 | 频率 | 判据 |
|---|---|---|---|
| **L1 契约测试** | Engine 自身的单测（状态机迁移、verdict 解析、DAG 无环、预算计算） | 每次改动 | 全绿 |
| **L2 端到端冒烟** | 用 **fake worker**（本地脚本，不调 LLM、不烧 token）跑完整链路 | 每次改动 | 全链路状态正确 |
| **L3 红队/反向测试**（你的既有偏好） | 注入故障：假 PASS、超时、死循环、空转、串行伪并行、非法 next_actions、证据篡改 | 每阶段 Gate | 守卫**必须拦住**；拦不住即 Gate FAIL |
| **L4 真实验证** | 在真实小项目上跑 1 个完整 phase | 每阶段末 | 产物可用 + 并行度达标 + 无人工干预 |
| **L5 长时压测** | ≥2 小时无人值守 | P5 | 无崩溃/死锁/空转 |

**反向验证铁律**：任何"修复"必须能**复现原 bug**——先证明旧实现失败、新实现通过，两次结果都留证据。禁止"改完看着对了就结案"。

## 8. 交接协议（每阶段换新对话的落地方法）

### 8.1 三步法

```
 ① 封板 (Seal)   scribe 生成/更新 HANDOFF.md + 冻结 state 快照 + 打 tag
 ② 清空 (Clear)  关闭当前对话（上下文丢弃 —— 这不是损失，是设计）
 ③ 重放 (Replay) 新对话只读 HANDOFF.md + engine brief → 继续推进
```

### 8.2 `HANDOFF.md` 固定栏目（沿用你项目里 progress.md 的习惯）

```markdown
# HANDOFF — <项目名> — <阶段> — <时间戳>
## 1. 状态快照        ：当前 phase / 任务统计(DONE/RUNNING/PENDING/ESCALATED) / 预算余量
## 2. 已完成          ：本期完成的产物清单（路径 + 一句话作用）
## 3. 关键决策        ：决策 → 理由 → 影响（**不允许只写结论**）
## 4. 未决问题        ：待决策项 + 各选项 + 我的倾向
## 5. 可证伪假设      ：当前依赖的假设 + 若假设错了会怎样 + 如何证伪
## 6. 下一步          ：next_actions（可直接执行）
## 7. 给新会话的上下文 ：只写"读哪些文件"和"不要读什么"，**不复述内容**
```

### 8.3 交接的三条纪律
1. **交接文档不写内容，只写指针**——新会话需要细节就去读文件，不要在 HANDOFF 里复制正文（否则 HANDOFF 自己变成上下文炸弹）。
2. **交接必须可证伪**：HANDOFF 里的每条结论都要带"证据路径"，新会话能自己复核。
3. **不交接"感觉"**：禁止"我觉得还差一点""基本可用"这类描述；要么有 Gate 证据，要么明确写 UNVERIFIED。

## 9. 风险与反模式（提前避坑）

| 风险 | 表现 | 对策 |
|---|---|---|
| **伪并行的自我欺骗**（最大风险） | 看起来多角色，实际同轮串行 | M1–M6 指标 + P2 红队 Gate（G2.6） |
| **主智能体上下文膨胀** | 主 Agent 开始"顺手看一眼"产出 → 上下文爆炸 → 决策质量崩 | 工具白名单 + brief ≤2KB 硬断言（G3.2）+ 严禁产物正文 |
| **假 PASS 污染** | worker 报喜不报忧，错误被固化 | 无证据=FAIL + 异源 Verifier + 证据哈希 |
| **真并行的写冲突** | 两个 worker 改同一文件互相覆盖 | git worktree 隔离（P2 必做，不能省） |
| **无限重试烧配额** | 一个任务卡住，循环空转 | 四级升级 + 预算熔断 + 防空转守卫 |
