## 2. Codex 主脑架构

### 2.1 为什么"主脑 ≠ 常驻进程"

若让一个 Codex 会话从头跑到尾，它必然：上下文持续膨胀 → 忘记早期约束 → 调度决策质量衰减 → 退化为自己动手干（即用户最担心的伪协作）。

因此把"循环"与"决策"再次拆开：

| 层 | 是谁 | 生命周期 | 职责 |
|---|---|---|---|
| 循环 | **文件状态 + 编排提示词** | 常驻（磁盘） | 记录"做到哪、谁在做、结果如何" |
| 决策 | **Codex 主脑**（`codex exec` 一次） | 无状态，用完即弃 | 读 brief，出 `next_actions[]` |
| 执行 | **子智能体**（编制内 7 人 + 外聘） | 按任务 spawn | 干活 + 写 verdict |

**主脑每轮只吃两样东西**：`state/brief.json`（≤2KB 机器摘要）+ `HANDOFF.md` 尾部 10 行。**永不读代码正文、永不读子智能体产出正文**。

### 2.2 三种唤醒模式

| 模式 | 命令 | 适用 |
|---|---|---|
| **单轮决策**（默认） | `codex exec -C <ws> "<主脑提示词> + <brief>"` | Engine 检测到屏障满足 |
| **会话续接** | `codex exec resume --last` / `codex resume --last` | 需要主脑保留角色记忆 |
| **异步注入** | `codex queue "<msg>"` | 向运行中的会话投递消息（真并行通信） |
| **派生分支** | `codex fork --last` | 需要"平行试两个策略" |

> `codex agents` 可枚举本地 app-server daemon 上所有 agent 会话 → 这是**真并行的可观测入口**（用于 M1-M6 并发度验证）。
> 以上命令均取自 `E:\Codex\bin\codex.exe --help` / `exec --help` 实测输出。

## 3. 双向调用桥（Cross-Host Bridge）

### 3.1 三条通道

```
┌────────────────────────┐                    ┌────────────────────────┐
│      Codex 宿主         │                    │     WorkBuddy 宿主      │
│  codex.exe (E:\Codex)   │                    │  codebuddy (@genie)     │
└───┬────────────────┬───┘                    └───┬────────────────┬───┘
    │ B1 原生 subagents│ B2 文件总线                │ B2 文件总线      │ B1 原生 TeamCreate
    │  codex agents    │ .swarm/bus/               │ .swarm/bus/     │  + Agent spawn
    │  codex queue     │  (零依赖·兜底)             │                 │  + SendMessage
    ▼                  ▼                          ▼                 ▼
┌───────────────────────────────────────────────────────────────────────┐
│  B3 跨宿主 CLI 调用   WorkBuddy ──→ codex exec  ✅ 参数已实测          │
│                       Codex ──→ codebuddy ...   ⚠ 参数待实测          │
└───────────────────────────────────────────────────────────────────────┘
```

| 通道 | 方向 | 机制 | 状态 | 可靠性 |
|---|---|---|---|---|
| **B1 原生** | 宿主内 | WorkBuddy：TeamCreate + Agent + SendMessage；Codex：subagents + `codex exec` | ✅ 可用 | 高（推荐主力） |
| **B2 文件总线** | 双向 | `.swarm/bus/inbox|outbox|verdicts/`，双方读写同一目录 | ✅ 零依赖 | **最高（保底）** |
| **B3-CX** | WorkBuddy → Codex | `codex exec -C <wt> -m <model> -s workspace-write "<task>"` | ✅ 已实测 | 高 |
| **B3-CB** | Codex → WorkBuddy | `codebuddy`（`cli\bin\codebuddy`，别名 `cbc`） | ⚠ **接入前必须先实测 headless 参数** | 未知 |

### 3.2 桥接命令集（已实测部分）

```bash
# WorkBuddy → Codex（在子 worktree 里跑一个独立子智能体，真独立进程）
codex exec -C <worktree> -m <model> -s workspace-write "<task-spec + verdict协议>"

# 需要完全放行时（仅限已外部沙箱化的环境）
codex exec --dangerously-bypass-approvals-and-sandbox -C <worktree> "<task>"

# 只读侦察（如 scout 探测 Codex 侧可用能力）
codex exec -s read-only "<probe>"

# 枚举并行会话（拿真并行证据）
codex agents

# 向运行中的会话异步投递（跨会话消息）
codex queue "<msg>"

# 插件市场操作
codex plugin list --json
codex plugin add <plugin>@<marketplace>
```

### 3.3 桥接铁律

1. **B3 永远只是加速器，B2 永远是兜底**。任何跨宿主任务必须在 `.swarm/bus/` 留下可离线读取的凭证；B3 调用失败不得导致任务丢失。
2. **跨宿主任务必须带完整说明书**。对端宿主看不到本宿主的对话上下文，说明书必须自包含（目标 / 输入路径 / 验收标准 / verdict 协议 / 权限边界）。
3. **跨宿主不共享上下文，只共享文件**。禁止把本宿主的聊天历史"喂"给对端。
4. **一条任务只由一个宿主的一个智能体执行**，禁止同一任务双宿主并发执行（会产生写冲突与双份 verdict）。
5. **失败即降级**：B3 调用 3 次失败 → 自动落到 B2 并要求人工/下一轮 Engine 领取。

## 4. 子智能体编制：编制内 + 外聘

这是本架构对"子智能体包含哪几种"的回答——**子智能体不是一个扁平列表，而是两层**。

### 4.1 编制内（7 人，固定骨架）

| Agent ID | 花名 | 职业 | 职责一句话 | 宿主 |
|---|---|---|---|---|
| `swarm-team-lead` | 隋调度 | 总调度长 | 只调度不干活，读判定出调度指令 | 主脑所在宿主 |
| `scout-router` | 甄可选 | 资源猎人 | 拉热度榜、建能力地图、选出主派与备胎 | 双宿主 |
| `planner-splitter` | 许分明 | 拆解参谋 | 一句话任务 → 可独立验收任务集 + 依赖图 | 双宿主 |
| `builder-core` | 寇图灵 | 主力编码官 | 按说明书实现，写最小证据 | 优选 Codex |
| `tester-breaker` | 查必现 | 破防测试官 | 主动构造反例与边界破坏 | 优选 Codex |
| `verifier-independent` | 严佐证 | 独立验收官 | **异源**复核，无证据即判 FAIL | **必须与 builder 不同厂商** |
| `scribe-handoff` | 纪长明 | 交接书记官 | 双轨日志、状态封板、生成 HANDOFF | 双宿主 |
| `bridge-crosshost` | 连两岸 | 跨宿主桥接官 | 跨宿主投递/回收/降级 | 双宿主 |

### 4.2 外聘（按热度榜动态招募）

候选池三类，全部由 `scout-router` 维护：

| 池 | 来源 | 枚举方式 |
|---|---|---|
| P1 WorkBuddy 专家 | 专家中心（含**热度榜**） | 枚举 `plugins/marketplaces/*/marketplace.json` + 专家中心榜单 |
| P2 Codex 插件 | Codex 插件市场 | `codex plugin list --json`（含 `--available`） |
| P3 Skill | 双宿主 skill 目录 | `$CWD/.agents/skills`、`$REPO_ROOT/.agents/skills`、`~/.agents/skills`、`~/.workbuddy/skills` |

**外聘不是替代编制内**，而是给编制内角色补领域能力：例如 `builder-core` 需要造 PPTX，则外聘「演示文稿专家」执行子任务，产出仍以 `outbox/` verdict 回流主脑。

### 4.3 三层调度的关系

```
                 ┌──────────────────────┐
                 │ 主脑 swarm-team-lead │  只决策
                 └───────┬──────────────┘
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
  编制内角色        编制内角色         编制内角色         ← 编排层（稳定）
  scout/router      builder-core      verifier
       │                 │
       │  外聘（按热度榜） │
       ▼                 ▼
  WorkBuddy 专家    Codex 插件/Skill                    ← 能力层（动态）
  高产创作者团队    pptx 插件
```

## 5. 热度榜调度策略（可在协议层配置）

> 依据：用户要求"选用/调动专家时，从热度榜最高的开始调度"。

### 5.1 硬顺序（不可调换）

```
S0 硬门槛过滤   ← 先筛，不看热度
   ① 能力覆盖：专家/Skill 的能力域 ⊇ 任务所需能力域
   ② 宿主可达：已安装 或 市场可获取
   ③ 权限足够：不会因权限不足必然失败
   不满足任一条 → 直接淘汰，**热门也不选**

S1 候选排序   ← 只在 S0 存活集合内排序
   ① 热度/榜单排名升序（WorkBuddy 专家中心热度榜、Codex 市场目录排名）
   ② 本地已安装 > 需下载安装
   ③ 能力域命中数多者优先
   ④ 成本 / 时延（仅当 ①②③ 全同分）

S2 派单
   取 Top-1 为**主派**，Top-1 为**备胎**（失败升级用）

S3 记录（写 decisions.md）
   候选池全量 / 各自热度排名 / 入选理由 / 备胎 / 榜单拉取时间

S4 反噬保护（关键）
   · 热度只决定"先试谁"，**不决定"信谁"** —— 所有产出一律过 verifier-independent
   · 同一外聘专家连续 2 次 FAIL → 写入 experience/patterns.md 降权
   · 榜单缓存 TTL = 24h；每阶段开始必须重拉（榜单有时效性，不凭旧排名）
   · 热度数据不可得时 → 退化为 ②③④ 排序，并在 decisions.md 标注"榜单缺失"
```

### 5.2 一句话记忆

**"热度决定顺序，证据决定采信。"**

## 6. 部署路径（两条，同一份包）

### 6.1 形态 A：WorkBuddy 专家团

```bash
# 专家必须生成到专家目录，否则不会被检测到
python3 scripts/init_expert.py agent-swarm --type team \
  --path "$WORKBUDDY_CONFIG_DIR/plugins/marketplaces/my-experts/plugins"
# 填入 plugin.json / agents/*.md / settings.json / avatars
python3 scripts/validate_expert.py <expert-dir>
python3 scripts/register_expert.py <expert-dir>     # 写入 marketplace.json
python3 scripts/package_expert.py  <expert-dir>     # 产出可分享 zip
```
> 用户使用时：专家中心 → 我的专家 → 选择「蜂群调度中心」→ 丢一句任务。

### 6.2 形态 B：Codex 插件

```bash
# 仓库级市场（团队内分发）
mkdir -p .agents/plugins
# 写 .agents/plugins/marketplace.json，指向本包
codex plugin add agent-swarm@<marketplace-name>
codex plugin list --json          # 验证已装
# 使用：新会话 /new 后
#   $agent-swarm:agent-swarm      显式调用
#   或直接描述任务让 Codex 隐式激活
```

### 6.3 形态 A + B 共存

同一目录同时被两宿主读取；`agents-fragment.md` 由 Codex 侧 postinstall 注入到项目 `AGENTS.md`（Codex 不会自动合并 AGENTS.md，需脚本处理）。
