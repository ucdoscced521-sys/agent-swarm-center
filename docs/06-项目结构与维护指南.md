## 1. 仓库总览与设计原则

```
multi-agent-plugin/
├── README.md                        项目入口（GitHub 首页）
├── CHANGELOG.md                     版本变更记录
├── .gitignore / .gitattributes      忽略规则；强制 *.cmd 为 CRLF
├── agent-swarm/                     ★ 唯一交付物：可安装的专家包（33 文件）
├── docs/                            设计与人读文档（6 篇）
├── scripts/                         运维脚本（上传/推送）
└── swarm-lab/                       验证实验台（可重跑，非交付物）
```

### 2.0 `scripts/`（运维脚本，2 个）

| 文件 | 作用 | 何时用 |
|---|---|---|
| `gh-device-auth.ps1` | **无 TTY 环境下的完整上传链**：自驱动 OAuth 设备码 → `gh auth login --with-token` → 建私密仓库 → 推分支 + 推标签 | 首次上传，或任何"`gh auth login --web` 拿不到验证码"的场合 |
| `push-to-github.ps1` | 已登录后的**一键推送**（自动探测便携版 gh；未登录时给出两条路径） | 日常增量推送 |

> **为什么需要 `gh-device-auth.ps1`**：`gh auth login --web` 需要 TTY。在沙箱/重定向输出的 shell 里它会以
> `unexpected EOF` 或 `context deadline exceeded` 失败，验证码虽被复制到剪贴板但进程已退出，无法使用。
> 该脚本绕开交互式流程自己调 GitHub 的设备码端点，因此可在无 TTY 环境下工作。
> 参数：`-RepoName` `-Visibility` `-CreateRepo` `-RepoPath` `-Proxy`；日志写到 `%TEMP%\gh-device-auth.log`。

### 三条设计原则（改东西前先读）

| 原则 | 含义 | 违反的后果 |
|---|---|---|
| **单源契约** | `schemas/verdict.schema.json` 与 `contracts/master-capability.json` 全仓只有一份权威版本，`agent-swarm/` 与 `swarm-lab/` 里的是**同一份的副本**（接线校验会做字节比对）| 会出现"两份差不多的 schema"，产出人声明 PASS 却过不了闸（真实事故 D-011）|
| **状态落盘，对话可弃** | 任何进展必须落 `.swarm/`，否则视为未发生 | 新会话无法续跑 |
| **运行时以 cache 为准** | 专家包真正被加载的位置是 **运行态 cache**，不是市场源 | 改了没生效、召唤出来还是旧版 |

## 4. 单源契约与同步模型

```
        <repo>/agent-swarm/            ← 权威源（唯一编辑目标）
                 │
                 │  sync-expert.mjs
                 ▼
   ①WB 市场源  ②WB 运行态 cache  ③Codex 市场源  ④Codex 缓存A  ⑤Codex 缓存B
        │              ★                │              │              │
        └── ①是编辑目标，②④⑤带版本号目录，换版本时旧目录不会自己消失 ──┘
```

**同步脚本的三道保险**（都是血换的）：

1. **源标记检查** —— 源里缺关键标记就**拒绝同步**（防止用旧内容覆盖已装包）
2. **同步前快照** —— 备份到 `runs/sync-backup/<ts>/`
3. **字节比对** —— 同步后逐文件比对运行态 cache 与源

## 5. 常见改造场景

### 5.1 改一个角色的行为

1. 改 `agent-swarm/agents/<角色>.md`
2. 若涉及**新规矩**，同步写进 `skills/agent-swarm/references/protocol.md` 与 `agents-fragment.md`
3. `node swarm-lab/tools/sync-expert.mjs`
4. `node swarm-lab/tools/run-step6-wiring.mjs`（W6 会验 frontmatter 是否被改坏）

### 5.2 改判定契约（**最需要小心**）

1. 改 `agent-swarm/schemas/verdict.schema.json`
2. **必须**同步所有引用它的地方：`protocol.md §2`、`builder-core.md`、`tester-breaker.md`、`verifier-independent.md`
3. **严格模式硬约束**：每个 object 的 `properties` 必须**全部**列进 `required`（不允许可选字段），`additionalProperties: false`
4. `node swarm-lab/tools/run-step3.mjs`（8/8）
5. **`node swarm-lab/tools/run-step5a.mjs 1`** ← 过一次真 provider，**不能省**（自家校验器通过 ≠ provider 接受）

### 5.3 加一个角色

1. `agent-swarm/agents/<新角色>.md`，frontmatter **必须**含 `name`（= 文件名）/`description`/`displayName`/`profession`/`maxTurns`，**禁止** `tools` 字段
2. 在 `agent-swarm-team-lead.md` 的角色表里登记 + 说明何时派它
3. 若它产出判定 → 走同一份 `verdict.schema.json`
4. 画头像 → 放 `avatars/`（512×512，裁掉水印）
5. 接线校验 W6 会验 frontmatter，W4 会验判定引用

### 5.4 改成本纪律

1. 改 `protocol.md §11`
2. 同步 `agent-swarm-team-lead.md`（Phase 3 成本纪律 / Phase 5 复核分级）
3. 同步 `builder-core.md`（证据摘要化 / 读取预算）、`scout-router.md`（探索预算）、`scribe-handoff.md`（主账瘦身）

### 5.5 加一步验证

1. 在 `swarm-lab/tools/` 加 `run-stepN.mjs`，**必须**：自己写报告文件（不要只 print）、退出码即结论、**每个断言配一个负向对照**
2. 在 `VALIDATION-SUMMARY.md` 登记
3. 本文件 §2.3 补一行

## 7. 发布流程（发版清单）

```powershell
# 1) 改版本号（两处 plugin.json）
# 2) 同步五落点
node swarm-lab/tools/sync-expert.mjs

# 3) 校验 → 注册 → 打包
python <expert-manager>\scripts\validate_expert.py "<落点1>"
python <expert-manager>\scripts\register_expert.py "<落点1>"
python <expert-manager>\scripts\package_expert.py  "<落点1>"

# 4) 再同步一次（settings.json 会被应用异步移除，需补位）
node swarm-lab/tools/sync-expert.mjs

# 5) 接线校验
node swarm-lab/tools/run-step6-wiring.mjs          # 期望 9/9

# 6) 回归
foreach ($n in 1..4) { node swarm-lab/tools/run-step$n.mjs }   # 16/16 18/18 8/8 26/26

# 7) Codex 侧换版本
codex plugin remove agent-swarm@personal
codex plugin add    agent-swarm@personal --json   # 期望 version = 新版本

# 8) 入库与打标签
git add -A
git commit -m "chore(release): agent-swarm vX.Y.Z —— <要点>"
git tag -a vX.Y.Z -m "..."
git push origin master --tags
```

> ⚠️ **顺序不能变**：`register` 之后不要立刻宣称"已是最新"，要**先补位再校验**。

## 8. 踩过的坑速查（改之前先看，能省你半小时）

| 坑 | 症状 | 根因 / 解法 |
|---|---|---|
| **漏运行态 cache** | 改了没生效，召唤出来还是旧版 | 必须同步 5 个落点；比对源与 cache 字节 |
| **漏 `.codex-plugin/.codebuddy-plugin`** | Codex 一直装旧版本 | 版本号在那两个目录里，同步清单必须包含 |
| **`settings.json` 消失** | validate 报 `Team type must have settings.json` | 应用异步移除（实测 30 秒内）→ 同步脚本末尾会补位 |
| **双调度根** | 主脑过闸全报 `no_verdict` | 说明书里 `SWARM_DIR` 必须写**绝对路径** |
| **自家校验器过 ≠ provider 接受** | 真模型调用 400 | 严格模式要求 `properties` 全进 `required`；改 schema 后必跑 step5a |
| **用旧源覆盖已装包** | 整轮改动静默消失 | sync-expert 的源标记检查会拦住；另有 `modify_backup` 可恢复 |
| **JS 正则 `(?m)`** | `SyntaxError: Invalid group` | JS 不支持内联标志，用 `/.../m` |
| **粗正则截断任务号** | 误报"泄漏/缺号" | 用字面量 + 词边界，别用 `T-\d+` |
| **审计轨被清空** | 前序证据静默消失 | `events.jsonl`/`main-log.md` **任何步骤都无权清空** |

## 9. 出事故时怎么恢复改动

WorkBuddy 会在 `~/.workbuddy/workspace/sessions/<会话ID>/modify_backup/` 保存文件编辑历史。

- 命名：`<序号>.<kind>.<hash>.<原文件名>`
- **`kind=m`** = 修改后的内容（**要的就是这个**）；`kind=a` = 0 字节删除标记（别用）
- **恢复方法**：按**文件尺寸逐一对上**再还原（尺寸是唯一可靠的对照锚点）
- ⚠️ 恢复后**必须再跑一次接线校验** —— 容易漏文件（不含关键标记词的文件检索不到）
