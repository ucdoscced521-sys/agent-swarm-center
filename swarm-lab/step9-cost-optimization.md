# 成本优化方案（一次小项目 ≈ 200 积分 → 目标 < 100）

> 基准样本：一次真实运行（09-25 23:55 → 09-26 01:41，**1h46m**，`deepseek-v4.1-flash`，**≈200 积分**）
> 任务规模：26 个派单 / 11 个 wave / 11 个 subagent，产出一个可交付的小项目
> **判断：这个量级明显偏高。** 钱主要不是花在"干活"上，而是花在**重复劳动与上下文搬运**上。

---

## 1. 诊断：钱到底花在哪（全部有证据）

| # | 成本源 | 证据 | 量级 |
|---|---|---|---|
| 1 | **复核 1:1 全覆盖** | 26 派单里含 **10 个独立复核**；每个复核都要**重跑测试 + 重读代码** | 🔴 **最大头** |
| 2 | **大文件反复进上下文** | 单份 `npm-test` 日志 **12–61KB**，被多个任务各读一遍（`run1` / `run2` / `x2` / `5files` / `fullsuite`…） | 🔴 很大 |
| 3 | **子智能体探索过度** | 单个 subagent 记录 **2.0–3.3MB**（11 个共约 16MB） | 🔴 很大 |
| 4 | **同一套测试重复跑** | 88 个测试被反复执行；仅 `npm-test*.txt` 就有 **8+ 份**，合计 **190KB+** | 🟠 中 |
| 5 | **派单过细 + 补派** | 26 派单 / 11 wave，含**空 wave**；`T-307b/308a/309/310/311` 多为事后补派 | 🟠 中 |
| 6 | **主账过胖** | `tasks.json` 27KB / `decisions.md` 21KB / `HANDOFF.md` 17.5KB，主脑与新会话反复读 | 🟠 中 |
| 7 | **收口后追加** | `T-311` 在宣布收口之后才落地 → 多走一整轮 | 🟠 中 |

**一句话**：**不是任务太大，是同一份信息被反复搬运。**

---

## 2. 对策：八条纪律（已写进协议，agent 会默认执行）

| # | 纪律 | 具体做法 | 预计省 |
|---|---|---|---|
| **S1** | **复核分级** | R3 高危（碰真实数据/删文件/改公开契约）**必复核**；R2 中危（新功能/改核心逻辑）**抽检 ≥50%**；R1 低危（文档/注释/文案/只读审计）**免复核**但须留痕 | **30–40%** |
| **S2** | **证据摘要化** | **禁止把 >8KB 命令输出塞进回流**；判定里只回 `{exit_code, 用例数, 失败数, 首条失败}`，原始日志**落盘只给路径**，复核人按需读片段 | **10–20%** |
| **S3** | **测试一次跑、多处引用** | 同一 wave 内测试**只跑一次**，其他任务**引用同一证据路径**，禁止各跑一遍 | **10%** |
| **S4** | **读取预算** | 说明书必须写"最多读 N 文件 / 最多跑 M 命令"（默认 **15 / 12**）；**禁止全仓 grep**，定位靠按路径精确读 | **10–15%** |
| **S5** | **模型分级路由** | 主脑 + 复核用强模型；侦察 / 拆解 / 书记 / 纯文档类用**快模型** | **5–15%** |
| **S6** | **派单合并** | 同一文件内改动**合并为一个任务**；禁止"一句话改动开一个任务" | **5–10%** |
| **S7** | **收口冻结** | 宣布收口后**不得再派单**；追加须开新阶段并重过 Exit Gate | **5%** |
| **S8** | **主账瘦身** | `tasks.json` 整体 **<5KB**，明细移 `tasks.detail/<id>.json` 按需读；`decisions.md` 每条 ≤5 行 | **5%** |

> 预计合计 **省 45–60%**：**≈200 积分 → 80–110 积分**。
> 其中 **S1 是唯一的大杠杆**——它单独就能把最大那笔开销砍掉一半以上。

---

## 3. 🔴 红线：不许为了省钱砍掉的东西

证据存在性校验 ｜ **R3 高危任务的独立复核** ｜ 真实时间戳 ｜ 未验项登记

> **省钱只能省"重复劳动与上下文"，不能省"证据与复核"。**
> 一旦为了省钱让校验变松，前面所有验证工作（91 条断言）就白做了。

---

## 4. 推荐参数模板（小项目直接用）

写进 `contract.md` 的 `BUDGET`：

```
BUDGET:
  单任务时限      ≤ 10 min
  单阶段迭代      ≤ 2 轮
  单任务读取      ≤ 15 个文件
  单任务命令      ≤ 12 条
  全局 token 上限  ≤ 300k（超限暂停并上报）
CONCURRENCY: 3（上限 5）
BATCH_SIZE:  1
VERIFY:
  R3 必复核 ｜ R2 抽检 50% ｜ R1 免复核(留痕)
  异源目标级别: L3 优先，达不到用 L2（须标注）
```

**预期**：同类小项目 **≤ 1h / ≤ 100 积分**，且交付质量与证据完整度不降。

---

## 5. 怎么持续核算（别只看感觉）

1. **每 wave 结束**，主脑在 `main-log.md` 记一行：`wave / 派单数 / 复核数 / 估算 token`
2. **收口报告第 7 栏 = 成本**：派单数 · 复核数 · 估算 token · **与预算对比**
3. **超预算即暂停上报**，不得自行续跑（已写进协议 §11.3）
4. 复核工具：`node tools/audit-real-run.mjs "<workspaceDir>"` —— 顺带产出复核覆盖率（`verifier/生产者` 比值），**这个比值是成本健康度的直接指标**：接近 1:1 说明 S1 没生效

## 6. 本次真实运行的复核覆盖率对照

| 指标 | 那次实测 | 应用 S1 后预期 |
|---|---|---|
| 派单数 | 26 | 18–20（S6 合并） |
| 独立复核 | **10**（≈1:1） | **4–5**（R3 全复核 + R2 抽检 50%） |
| `npm test` 执行次数 | 8+ 次 | **2–3 次**（S3） |
| 大日志进上下文 | 190KB+ | **< 20KB**（S2） |
| 主账读取量 | 65KB+ | **< 15KB**（S8） |

---

## 7. 一句话

**这次贵不是因为任务大，是因为同一份信息被搬了很多遍。**
八条纪律里 **只做 S1 + S2 + S3 三条，就能省掉大头**，而且**不损失任何证据与复核强度**。
