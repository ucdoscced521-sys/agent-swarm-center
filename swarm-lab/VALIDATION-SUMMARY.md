## 2bis. Step 5A 的关键发现（比"通过"更重要）

### 🔥 自家校验器通过 ≠ provider 接受

Step 3 的契约在自家校验器上 **8/8 通过**，但真实 provider **直接拒收**：

```
Invalid schema for response_format 'codex_output_schema': 'required' is required to
be supplied and to be an array including every key in properties. Missing 'duration_s'.
```

**严格结构化输出模式要求：每个 object 的 properties 必须全部出现在 required 中** → 不允许"可选字段"。
已修：`metrics` 砍到 3 个必填字段，`handoff` 改必填。改完重跑 Step 3 仍 **8/8**（无回归）。

> **这类问题假 worker 测试结构上不可能发现。** 这是 Step 5 存在的唯一理由。
> **铁律：每次改判定契约，都必须过一次真 provider 的最小调用。**

### 真模型实测

| 项 | 值 |
|---|---|
| schema 遵从率 | **3/3** |
| 输出字节 | **182B，三次完全一致**（仅任务号不同）|
| 单次耗时 | **42.6s / 56.2s / 181.1s（方差 4 倍）** |
| 模型 / tokens | `gpt-6-astra` / 15,585 per call |

**耗时方差 4 倍** → 直接印证 Step 2 定的纪律：M1 并发度绝不能只测一次，"重跑 3 轮取 min"在真模型下**更关键**。

### `codex exec` 三个调用坑

| 坑 | 症状 | 解法 |
|---|---|---|
| 不关 stdin | `Reading additional input from stdin...` | `spawnSync({ input: '' })` |
| `-C` 目录不存在 | `os error 2` | 先 `mkdirSync` |
| 不在受信 git 仓库 | `Not inside a trusted directory ...` | 加 `--skip-git-repo-check` |

**输出流分工**：`stdout` = 最终答复（纯 JSON）；`stderr` = 会话转录。解析只取 stdout。

## 2ter. Step 5B 改道通过（原方案被沙箱拦两次）

### 原方案为什么失败

`-s workspace-write` 会让 codex 在 Windows 上**安装自己的 OS 级沙箱**，触碰 `AppData\Local\Microsoft\Windows\Caches`、`System32\CatRoot2\dberr.txt` → **被宿主沙箱拦截**。
**连续两次被拒**，被拦清单里连 `node.exe (执行)` 都在内；即使用户显式放行、加 `dangerouslyDisableSandbox`，在后台任务里仍被拦。
→ 判定：**被拦的不是"我们的文件写入"，而是 codex 装沙箱这个动作。**

### 改道方案：read-only + 产物作为数据

```
builder(-s read-only) → 返回 files:[{path,content}] + 自己的 verdict
        ↓ 编排层落盘（纯 I/O）+ 执行验收产出真实证据
gate 判定并【与实测结果对比】（不盲信自述）
        ↓
verifier(-s read-only) → 只看「源码 + 实验台原始输出」，不看 builder 结论 → 独立 verdict
        ↓ 比对两者
```

新契约 `schemas/builder-artifacts.schema.json`；`content` 设 `maxLength` 防夹带，`path` 落盘前校验不逃出 worktree。

### 实测结果（真模型一次写对）

| 项 | 值 |
|---|---|
| 耗时 | builder **50.2s** / verifier **49s** |
| 产出代码 | `fs/promises` + **`process.exitCode`**（比 `process.exit` 更稳，保证 stdout flush）+ null/array/非对象三重校验 |
| 实验台 AC1 | `sample.json → exit 0, stdout "3"` ✅ |
| 实验台 AC2 | `nope.json → exit 1` ✅ |
| 实测 vs 自述 | **一致**（未见虚报）|
| verifier 独立性 | 不同证据文件 + 不同 agent 名 + 未看 builder 结论 ✅ |

**代价（如实标注）**：验收命令由实验台执行，不是模型自己跑的。
但换个角度**更可信**——"代码到底对不对"由实测决定，而非采信模型自述。

**仍存的诚实边界**："异源"只是**不同会话、不同 agent 身份、同一底层模型**；真异源（不同厂商模型）未覆盖。

## 2. 每一步的关键证据

### Step 1 · 最小闭环
- **head-only 客观证明**：喂 200KB 正文的 verdict，主脑仅读 4096B（50x 差距）仍判对 → 上下文卫生从"声明"变"可量化"
- **4 类故障注入全被拦且归因精确**：`no_verdict` / `malformed_verdict` / `evidence_absent` / **`evidence_dangling`（假 PASS 典型形态）**
- 交付物**真能跑**（不只看断言）：`sample.json → 3, exit 0`

### Step 2 · 真并行（命门）
- 六指标：M1 并发度 / M2 时间线重叠 / M3 峰值进程 / M4 上下文隔离 / M5 写冲突隔离 / M6 会话独立
- **同一份 metrics 代码对 A 判 PASS、对 B 判 FAIL** —— 指标有区分力
- **每个指标都配了负向对照**：M1-M3←串行；M4←污染注入；M5←无隔离共用目录；M6←会话复用

### Step 3 · 判定硬化
- 文本版两个真实盲区被堵：
  - **夹带未声明字段**（`approve:true`）→ 文本版 PASS，JSON 版 `schema_violation`
  - **张冠李戴**（TASK 写别的任务号）→ 文本版 PASS，JSON 版 `task_mismatch`
- 三层防御：结构层（Schema）/ 身份层（task 绑定）/ 事实层（证据存在性）

### Step 4 · 边界硬化
- **承重证明**：无守卫时危险动作真的写下 4 个文件；有守卫时 0 执行、**磁盘零残留**
- **结构性证明**：守卫源码零 `prompt` 字样 → 改提示词无法绕过
- 白名单：9 条放行 / 11 条拒绝 / 默认拒

## 4. 四步共同的元方法（可迁移）

1. **先假后真** —— 假 worker 验链路（0 cost），链路通了再换真智能体。把"链路问题"与"模型行为问题"分开定位。
2. **每个指标/断言配一个负向对照** —— 没有对照的指标只是"看起来在工作"。
3. **承重证明** —— 证明"没有它就会出事"，而不只是"它在返回 true"。
4. **逐行核对报告语义** —— 数字对但语义错，比挂掉更危险（会给出虚假的安心）。
5. **诚实标注未验证项** —— "只确认存在"与"已端到端验证"必须分开写，不混入结论。

> 补充观察：这四轮里**被测的 gate 一次没错，测试脚手架连错 5 次**。每次改脚手架都必须重跑并核对表格读得通不通。
